# Atomic Commit（アトミックコミット）スキル

コミット規約の正本は [.claude/rules/common/git-workflow.md](../../rules/common/git-workflow.md)。本スキルはそれを実行するための手順。

## 手順

1. **変更を俯瞰する**
   - `git status` で変更/追加/削除されたファイル一覧を確認する。
   - `git diff` （ステージ前）と `git diff --staged`（ステージ済み）で内容を確認する。

2. **関心事ごとにグルーピングする**
   - 「1機能追加」「1バグ修正」「1ドキュメント更新」「1設定変更」のように、意味のある最小単位を洗い出す。
   - 1ファイル内に複数の関心事の変更が混在している場合も分割対象にする。

3. **部分ステージする**
   - ファイル単位でよければ `git add <file>`。
   - 1ファイル内で関心事が混在する場合は `git add -p <file>` でハンクごとに選択する。

4. **ステージ内容を最終確認する**
   - `git diff --staged` で、これからのコミットに含まれる内容が1つの関心事に対応していることを確認する。

5. **Angular形式でコミットメッセージを作成する**
   - フォーマット: `<type>(<scope>): <subject>`
   - type: `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `chore`
   - subject: 命令形・現在時制、先頭大文字化なし、末尾ピリオドなし、100文字以内。
   - 必要なら body に変更の動機を追記する。

6. **コミットする**
   - `git commit -m "<type>(<scope>): <subject>"`（bodyが必要なら `-m` を複数回、またはヒアドキュメントで複数行メッセージを渡す）。

7. **残りの変更について1〜6を繰り返す**
   - `git status` が空になるまで、または残りが次の作業単位に属するとわかるまで繰り返す。

## チェックリスト

- [ ] 1コミットの diff を読んで、無関係な変更が混ざっていないか
- [ ] コミットメッセージの type が実際の変更内容と一致しているか（例: バグ修正なのに `feat` にしていないか）
- [ ] subject が命令形・現在時制になっているか
- [ ] デバッグ用の `console.log` や一時ファイルを混入させていないか
