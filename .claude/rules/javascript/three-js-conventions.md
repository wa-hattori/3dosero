# Three.js 規約（3D描画フェーズ導入時に適用）

まだ Three.js は導入していないが、導入時に迷わないよう先取りで規約化しておく。

## ロジックと描画の分離（最重要）

- `src/logic/` 配下のゲームロジックモジュールは `three` を **一切 import しない**。盤面状態はプレーンなJSオブジェクト/配列で表現する。
- `src/render/` 側が `src/logic/` の関数・状態を読み取ってシーングラフに反映する。逆方向（ロジックが描画に依存する）の依存は作らない。
- 石を置く操作のUIイベントは `src/ui/` → `src/logic/`（状態更新）→ `src/render/`（再描画）の一方向フローにする。

## シーン/カメラ/レンダラーの所有権

- `Scene` / `Camera` / `WebGLRenderer` のインスタンスは1箇所（例: `src/render/scene-manager.js` のようなモジュール）に集約して所有する。他のモジュールが直接 `new THREE.Scene()` 等をしない。
- カメラの視点操作（全体回転・拡大縮小、VESTA的な操作感）は `OrbitControls` 相当の1モジュールに閉じ込め、UIからはその公開APIのみ呼び出す。
- 層ごとに見るオプション（layer-slice view）は、既存のシーンに対して各層メッシュの `visible` / 透明度を切り替える形で実装し、層を切り替えるたびにシーンを作り直さない。

## リソース管理（メモリリーク防止）

- 盤面再構築などでメッシュを作り直す際は、古い `geometry` / `material` を必ず `dispose()` してから参照を破棄する。
- `Geometry` や `Material` はできる限り使い回す（石1個ごとに新規生成しない。色違いの2種のマテリアルを共有インスタンスとして持つ）。
- `requestAnimationFrame` のループは1つに統一し、ページ離脱やビューのアンマウント時にキャンセルする。

## パフォーマンス

- 8×8×8=512マスの石・マスをすべて個別メッシュにするとドローコール数が増えすぎる可能性があるため、`InstancedMesh` の使用を優先的に検討する。
- 着手可能マスのハイライト（灰色表示）は、マスの数だけ動的にジオメトリを生成するのではなく、あらかじめ用意したハイライト用メッシュの表示/非表示・座標更新で行う。

## レビュー観点

このカテゴリのコードは `three-renderer-specialist` エージェントでレビューする（未disposeのgeometry/material、ロジックとの依存方向、不要なシーン再構築などを重点的に確認）。
